## 总览

1.用户下单  ➡  mySQL插入【待付款 + 未支付】

​	⬇

2.用户点击支付  ➡  向微信端发起支付请求

​	⬇

3.用户在确认页付款  ➡  微信端标记成功，并HTTP回调商户

​	⬇

4.商户处理回调  ➡  验签 / nonce / 锁 / 短事务CAS →入库【待接单+ 已支付】



### 用户下单

1.前端带 `requestId` + 商品 → `POST /admin/order/mock`

### 用户点击支付

1.前端 `PUT /admin/order/mockPay/{id}`，然后打开确认页

2.后端将请求转给支付网关

3.支付网关调用requestPay 

1. 先校验订单和订单的状态
2. 调用redis.tryLock加短锁防止前端连点多次调用
   1. lockKey同一订单是一样的，所以可以互斥
   2. 等正常支付请求结束后finally会释放、或者TTL过期，同一订单又可以点击支付了。

3. 向微信发起支付请求
4. 然后释放短锁

### 用户在确认页付款

1.微信把订单标记SUCCESS，带 HMAC 签名，`POST` 商户 `notify_url`（有限次重试）

### 商户处理回调 

1.微信回调打到POST /admin/order/mockPay/notify

2.调用支付网关的handlePayNotify

1. 做空参校验

2. verifySignAndTimeWindow：HMAC验签防伪造，时间窗放过期重放

3. nonce去重：order:pay:nonce：{nonce} SET NX

   1. 第一次见这个nonce就继续入账
   2. 否则查库中的支付状态：已付直接返回成功，未付抛429异常，让微信端稍后重试

4. 按照商户订单号 `orderNumber`预查订单

   1. 没有订单：删掉刚才占位的nonce，抛冲突

5. 同单入账锁order:pay:lock:{orderId}（支付锁）

   1. 抢不到的单抛429支付处理中
   2. 防止同一订单并发回调一起冲入账逻辑

6. 开启短事务进行入库：payNotifyTxService.markPaidInShrotTx

   1. 调用TransactionSynchronizationManager.registerSynchronization注册解锁同步
      1. 事务提交后：afterCommit再投递副作用
      2. 事务结束后：afterCompletion释放支付锁
   2. 查单、核金额、状态校验
   3. casMarkPaid入库
   4. 同事务写insertOrderPaid，Outbox占位（事务性发件箱，是一种可靠发消息的模式：业务改库成功后，还要把「订单已支付」这类事件通知下游（库存、积分、推送、消息队列），但不能在事务里直接调 MQ——因为事务可能还没提交，或发完消息却回滚了）
   5. 事务结束后：afterCompletion 放支付锁；提交成功则 afterCommit publish
