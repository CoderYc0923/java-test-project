对照表：`db/changelog/changes/003-create-pay-outbox.sql`  
说明：按「先建立正确心智模型」整理；不展开 B+Tree 细节。

---

## 0. 先看表上的三条索引

```sql
UNIQUE KEY uk_event_id (event_id),
KEY idx_status_created (status, created_at),
KEY idx_order_id (order_id)
```

记住三句话：

1. **这三个都是索引**（都能帮助查找）
2. **字段 ≥ 2 个的叫联合索引** → 只有 `idx_status_created` 是联合索引
3. `uk_event_id`、`idx_order_id` 都是**单列索引**；`UNIQUE` 只是多了一层「不能重复」的约束

---

## 1. 唯一索引 vs 普通索引

### 1.1 各自主要干什么

| 类型 | 主要作用 | 附带作用 |
|------|----------|----------|
| **唯一索引** `UNIQUE KEY` | **保证列（或列组合）在表里不重复** | 也能加快按该列查询 |
| **普通索引** `KEY` | **加快查询**（WHERE / JOIN / ORDER BY 等） | 不保证唯一 |

用自己的话记：

- 表**需要**保证某列唯一 → 才建唯一索引  
- 表**不需要**唯一约束 → 不要为了「好看」乱建唯一索引；要加速就用普通索引  
- 若业务上「既要唯一，又常按该列查」→ 建唯一索引就够了，**不必**再给同列建一条普通索引

### 1.2 `uk_event_id` 到底为了干嘛

Outbox 写入时会带一个 `event_id`（例如某次「订单已支付」事件）。

- **有唯一索引**：同一 `event_id` 第二次插入会失败 → 库拦住重复源头 → 不会因为重试/并发多插一行，进而多发一次 MQ  
- **没有唯一索引**：可能插两行相同事件 → 扫描发送两次 → 下游就算做幂等也多挨一次重复投递

所以这里唯一索引的**第一意义是业务幂等约束**，不是「为了查得快才建」。

### 1.3 另外两条普通索引干什么

| 索引 | 类型 | 用途直觉 |
|------|------|----------|
| `idx_status_created (status, created_at)` | 联合索引 | 扫「待发送」：按状态筛，常再按时间排 |
| `idx_order_id (order_id)` | 单列普通索引 | 按订单查 Outbox 记录 |

同一 `status` 会有很多行，所以用**普通**联合索引，而不是唯一索引。

---

## 2. 联合索引与最左前缀

联合索引 = 一个索引里排了多列，例如 `(status, created_at)`。

**最左前缀**：一般要从**最左边的列**开始匹配，索引才好用。

| 条件 | 能否较好用到 `(status, created_at)` |
|------|-------------------------------------|
| `status = ?` | 能 |
| `status = ? AND created_at > ?` | 能 |
| 只有 `created_at > ?`（跳过 status） | 基本不能 |

注意：最左原则讲的是「联合索引**能不能被用上**」，不是「覆盖索引」。

---

## 3. 覆盖索引（别和联合索引搞混）

### 3.1 它是什么

**覆盖索引不是一种建索引的类型**，而是描述**某次查询**的效果：

> 这条 SQL 用到的列（`SELECT` 要的、`WHERE`，有时还有 `ORDER BY` / `GROUP BY`）  
> 是否都能从一个索引里拿到？  
> - **全都能** → 覆盖索引，**不用回表**，通常更快  
> - **缺任何一列** → 还要按主键回表取数据

和「是不是联合索引」「WHERE 是不是多字段」没有必然关系。

### 3.2 例子（对照本表）

假设：

```sql
SELECT event_id, order_id, status, created_at
FROM pay_outbox
WHERE status = 'NEW';
```

问两个问题：

1. **`idx_status_created` 走了吗？**  
   **可以走。** 条件是 `status = 'NEW'`，匹配联合索引最左列。

2. **还要回表吗？**  
   **要。** 索引里主要是 `status`、`created_at`（InnoDB 二级索引叶子上还会带主键 `id`），但 `SELECT` 还要 `event_id`、`order_id`，索引里没有 → 回表取这两列。  
   → **不是覆盖索引。**

若只查索引里已有的列，才更像覆盖：

```sql
SELECT status, created_at FROM pay_outbox WHERE status = 'NEW';
```

若坚持上面那条宽 `SELECT` 还想覆盖，索引列大致要能盖住用到的列，例如把需要的列也放进联合索引（是否值得另说，索引不是越宽越好）。

补充：优化器**不一定**每次都走索引。若几乎全表都是 `NEW`，可能直接全表扫更划算。概念上仍是：「条件匹配最左 → 可以用这条索引；要的列不全在索引里 → 用了也要回表」。

## 4. 一张总表（防再混）

| 说法 | 是什么 | 本表例子 |
|------|--------|----------|
| 索引 | 加快查找的结构；唯一索引还带约束 | 三条都是 |
| 单列索引 | 只索引一列 | `uk_event_id`、`idx_order_id` |
| 联合索引 | 一个索引多列 | `idx_status_created` |
| 唯一索引 | 索引 + 唯一约束 | `uk_event_id` |
| 普通索引 | 只加速，不保证唯一 | `idx_status_created`、`idx_order_id` |
| 最左前缀 | 联合索引怎么被 WHERE 用上 | 先匹配 `status` |
| 覆盖索引 | 本次查询是否不用回表 | 看 SELECT/WHERE 列是否全在索引里 |
| 回表 | 索引不够，再按主键回数据行取列 | 宽 SELECT + 窄二级索引时常见 |

---

## 5. 用自己的话收束（核对理解）

1. 三个都是索引；多字段的那条叫联合索引。  
2. 唯一索引主要保证表里唯一；不需要唯一就别建；普通索引主要为了加快查询。  
3. `event_id` 唯一：防止同一业务事件插两行 Outbox。  
4. 覆盖索引：一次查询用到的条件列和结果列是否都被某个索引盖住；盖住则不回表。  
5. 联合索引 ≠ 覆盖索引；最左原则 ≠ 覆盖索引。

---

## 6. 和 Outbox 流程的一点关系（可选）

- `uk_event_id`：写入侧幂等（同一事件只落一行）  
- `idx_status_created`：发送扫描侧加速（找 `NEW` / 按时间捞）  
- `idx_order_id`：按订单排查、补发时查找  

索引设计跟着**真实查询/约束**走，而不是先背名词再硬套。
