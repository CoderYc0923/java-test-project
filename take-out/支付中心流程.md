# 支付中心流程

```text
用户下单
	-> post /admin/order/mock -> 前端传递requestId
	-> 创建订单 -> 产生问题：用户连点 -> 解决办法：创建订单前通过redis的SET NX EX进行幂等key，若redis缓存中已经存在该订单，则返回缓存中的订单。若是第一次创建，则创建订单后，将订单ID存入redis
	-> 订单创建后，用户点击支付
	-> put /admin/order/mockPay/{id} -> 前端传递订单Id
	-> 产生问题：1.用户多次连续点击支付 2.用户多窗口点击支付（多渠道）
	-> 调用支付中心的requestPay进行支付
	-> requestPay中做了几件事
		-> 先检查库中的订单的支付状态，若订单已经支付了，就直接返回这笔订单，不调微信支付API
		-> 然后再校验订单的存在性以及订单状态和订单支付状态是否符合「待付款 + 未支付」，若不是则抛出异常
		-> 为了解决“1.用户多次连续点击支付”，对订单ID做redis的SET NX EX进行互斥锁
		-> 上锁动作后，再一次进行订单的检查，然后根据本次请求创建一个支付单
		-> 创建支付单前，先校验支付单表中是否存在支付状态为PAYING的支付单，在支付阶段防止“2.用户多窗口点击支付（多渠道）”，尽量不开第二笔同渠道支付单。
			-> 若存在，则用存在的支付单的支付单号outTradeNo，向微信支付API发起支付请求
			-> 若不存在，则生成一个支付单号outTradeNo并将支付单状态设置为PAYING以及是否正在支付payingFlag设置为1
	-> 微信支付API处理请求，并调用回调接口 post /admin/order/mockPay/notify
	-> 产生问题：3.微信支付api重复调用回调接口
	-> 调用支付中心的handlePayNotify
		-> 通过微信传回的Wechatpay-Nonce进行redis SET NX EX 做幂等，解决“3.微信支付api重复调用回调接口”
			-> 若已经见过这个nonceKey，去库里查询对应支付单和订单，若不存在，则抛异常;若存在且订单已支付或支付单成功活已退款，就返回这个订单。
			-> 若第一次见这个nonceKey，存入redis缓存，根据支付单单号outTradeNo去库里找对应的支付单
			-> 产生问题：4.同一订单在回调入账时被并发处理（多实例节点同时收到回调，微信补推/重试新nonce）
			-> 根据支付单中的订单ID加redis锁，解决问题“4.同一订单在回调入账时被并发处理（多实例节点同时收到回调，微信补推/重试新nonce）”
			-> 调用markPaidOrRefundInShortTx进行支付回库事务
				-> 将“根据支付单中的订单ID加redis锁”放到事务结束再解锁，防止提前解锁被别的请求抢到锁
					-> afterCommit 中，实现1.将其余同订单的支付单关闭，并发布消息 2.将本支付单退款
					-> afterCompletion中，将支付锁解锁
				-> 校验支付单和订单，若订单已经支付，则在事务提交后将本支付单退款，解决“2.用户多窗口点击支付（多渠道）”回调阶段多笔同订单支付单的问题。
				-> CAS入库并将本支付单状态改为已支付，并在事务提交后将其余同订单的支付单关闭
			
			
```
